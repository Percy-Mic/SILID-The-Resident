# 14 — Deliverables & Exit Gates (canonical)

**Precedence:** this doc is canonical for **proof** — what counts as done and what may be claimed. Doc 13 defines the order, doc 08 the calendar, docs 09/11/12 the how. The spec's phase contract is adopted **verbatim**: every phase produces DELIVERABLES and must pass its EXIT GATE; "code exists" is never completion; a failed gate = STOP → IDENTIFY → FIX → RETEST, never build dependents on a failed phase. The five major gates (A Playable Foundation · B Core Horror Loop · C Replayability · D Multiplayer · E Shipping) are **never skipped**.

**Environment law:** this repo cannot compile UE5 C++; compile/run/test happen at the user's editor session. Therefore this doc's authority in-repo is: deliverables are authored, self-reviewed against docs 11/12, feature-spec'd, and **gate reports are drafted and marked PENDING-COMPILE** until the user's editor run proves them.

---

## 1. Universal phase contract (spec §1, §37, §39)

REQUIREMENTS → DELIVERABLES → **DEPENDENCIES → RISKS → OWNERS → TARGET RESOLUTION** → IMPLEMENTATION → COMPILE → AUTOMATED TESTS → IN-GAME TEST → BUG FIX → EXIT GATE → NEXT PHASE. (The bolded middle steps are the doc-16 governance extension: every phase starts with a Phase Risk Review (15 §5 / 16 §8) and closes with an exit-gate report — an overdue CRITICAL risk blocks the phase automatically, 16 §6.) A feature is DONE only when: implemented + compiles + runs + tested + failure cases handled + architecture-compliant (09) + ownership-compliant (11) + dependencies valid + save-safe where required + multiplayer-safe where required + randomization-safe where required + documented. The assistant never says "implemented, so we move on" — it proves the gate report. **Regression gate (spec §36):** before each new phase, the previous phase's tests re-run; nothing silently breaks an earlier feature. **Blocking rule (spec §35):** a failed owner system blocks every dependent; fix the owner, never duplicate around it.

## 6. Working rules going forward

1. Every doc-13 phase closes with a §4-format gate report appended to this doc (or a per-phase report file), never a chat claim.
2. In-repo work produces deliverables + drafted reports marked PENDING-COMPILE; the user's editor session executes COMPILE/TEST/GATE and the report is upgraded or the phase reopens. **The procedure for that session is [21-first-editor-session.md](21-first-editor-session.md)** — its Stage 8 templates are the fill-in versions of this doc's format for P0/P2/P9.
3. A failing gate appends to BLOCKERS and the frontier returns to the failed phase (spec §1's STOP loop) — doc 13's frontier order only resumes when the gate passes.
4. Regression reports (spec §36) are part of every gate report: the previous phase's gate re-runs are listed before new-phase work begins.
5. GATE A→E transitions get their own consolidated reports (this doc §3 list), and none may be passed on PENDING-COMPILE.

## 7. P7 feature-spec block (doc 12 §9 — recorded at implementation)

**Classification:** `USILIDRepairComponent` = Component (C++, composed in BP) · `ISILIDRepairable` = Interface (additive, default impls) · `FSILIDRepairRequirement` = Struct (data rows on the component) · `FSILIDOperationResult`/`ESILIDFailureCode` = Structs (shared, SILIDTypes.h).

- **Owner:** the component owns one machine's repair state (condition, broken flag, applied work, current requirement row). Inventory state is NEVER touched except through the inventory's API.
- **Reads:** inventory capability queries (`HasToolForTag`, `HasKeyForTag`, `HasComponentForTag`), time (cooldown).
- **Writes:** its own condition/row/step state; inventory only via `ConsumeComponent` (the barrier's precedent).
- **Calls:** `NoiseEmitterComponent::EmitNoise` (work is loud — Noise.Device), optional AudioComponent.
- **CalledBy:** player interaction (E via `ISILIDInteractable::UseItem`/Interact on the owner actor), debug commands, future objectives.
- **Replicated:** server-authoritative; condition + row state replicate when multiplayer lands (P18–21); clients request work, server evaluates.
- **Saved:** explicit `SaveTo/LoadFrom` into the generic payload (Flags + Counters); load replays presses from data so requirement configuration changes never corrupt old saves.
- **Server/Client:** all evaluation server-side in MP; the result struct's Message drives client HUD prompts.

## 11. P8 feature-spec block (doc 12 §9 — recorded at implementation)

**Classification:** `UElectricalSystemSubsystem` = **WorldSubsystem** (game/PIE worlds only; doc 12 §1 type map) · `USILIDElectricPoweredComponent` = Component (C++, composed in BP) · `FSILIDPowerNode` = Struct (subsystem-owned) · `ESILIDPowerSourceState` = Enum (the doc 05 §2 machine states) · no new C++ actor — `BP_Generator` is a thin shell composing Repair + ElectricPowered(bIsGenerator) + NoiseEmitter (doc 09 §3 composition law).

- **Owner:** the subsystem is the SINGLE authoritative owner of power distribution — the node graph, per-node powered flags, the source state machine, fuel state, and overload timers (doc 11 §1 row). Devices own only their wish (`bDeviceEnabled`); the subsystem never writes it.
- **Reads:** the generator's repair condition (via its own component), the world clock (grace/fuel timers), registration state.
- **Writes:** only its own owned state + registration bookkeeping. Device reactions are the device's business.
- **Calls:** `RepairComponent::OnRepaired` (P7 fix input — observed, not polled), `NoiseEmitterComponent::EmitNoise` on the generator actor (start 0.9 / sputter 0.4 / breaker 0.6 — the doc 05 §2 risk/reward), save payload maps.
- **CalledBy:** the generator BP shell (Interact → `StartGenerator`, fuel spend → `AddFuel`), fusebox barriers (`SetFuseBlown` on clear), breaker-reset interactions, ElectricPowered BeginPlay/EndPlay registration, P13 objectives/HUD/audio via delegates, the P16 validator (`GetGeneratorActor` — read-only).
- **Replicated:** server-authoritative state machine (doc 05 §2 + 06 §2 authority list — "electricity" is server-owned); clients receive per-node enum + load at P18+; cosmetic flicker/jitter is client-local, never authoritative.
- **Saved:** generic payload maps keyed by stable ids — `power.generator.running` (flag), `power.generator.fuel` (counter), `power.fuse.<NodeTag>` (flags). Machine state is RE-DERIVED at load from repair/fuel data (the P7 replay law — saves never bake configuration); a load never restores mid-trip.
- **Server/Client:** all evaluation server-side; `FSILIDOperationResult` messages drive client prompts. Clients never solve power locally.

**Tick rule (doc 12 §10):** the subsystem never Ticks. One `FTimerHandle` at 1 Hz (`BoardTick`) — fuel economy, grace→trip conversion, and nothing else; the exact per-tick allowance doc 01 §6 grants the ElectricalSystem by name. Idle rooms cost nothing (event-driven fanout only).

**Event discipline (doc 12 §10):** `OnNodePowerChanged` / `OnGeneratorStateChanged` / `OnBreakerTripped` are subsystem buses (world-wide facts); `OnPowerChanged` on the component is actor-local. Each has exactly one owning class, documented in that class's EMITS header. Consumers never poll; the subsystem pushes every flip exactly once (`NotifyNodePowerChanged` → debounced re-broadcast).

**New risks:** none (the electricity protocol was pre-registered in doc 15 §5). **Existing risks affected:** R-005/R-027 contained (tag registry, zero hard refs — the doc 12 §11 bar: new powered machine = component + registration, no generator edits); R-016 contained (replay-safe generic maps); R-013 contained (one 1 Hz timer, no polling); R-007/R-008 mitigated further (the power chain joins the P16 graph — `Machine.Power` grounds generator/fusebox dependencies before play).

**Rollback plan:** the system is additive — reverting the six touched files (Door/Barrier/EscapeRoute/LightSwitch/RepairComponent/Tags) restores the pre-P8 behavior byte-for-byte; the two new files simply drop out. No existing save format change (additive map keys only).

## 13. P13 feature-spec block (doc 12 §9 — recorded at implementation)

**Classification:** `USILIDObjectiveSubsystem` = **WorldSubsystem** (game/PIE worlds only) · `USILIDObjectiveData` = **UPrimaryDataAsset** (story rows — DA_Story content, joins `USILIDItemData` in the type map) · `FSILIDObjectiveState` = Struct (subsystem-owned) · `Story.*` tags = native grammar (SILIDTags — system facts, not story nouns) · no new actors/components: the fabric LISTENS; the puzzle types (Safe/Radio/CodeLock/Barriers) already exist from the slice.

- **Owner:** the subsystem is the single authoritative owner of objective state — the active/completed/failed sets, progress counts, and the story-tag ledger (doc 11 §1). Data rows own their definitions; world systems keep their own facts; the subsystem only derives.
- **Reads:** world events via delegates ONLY — GameMode `OnEscapeReached`, `USILIDRepairComponent::OnAnyRepaired` (new component-static fabric broadcast), Electrical `OnGeneratorStateChanged` / `OnBreakerTripped` / `OnNodePowerChanged`. Nothing polled, no world scans.
- **Writes:** only its own owned state + raw-fact save keys. Never writes inventory/AI/doors/power — completing an objective READS what happened (doc 11 §2 upward law).
- **Calls:** log macros (`LogSILIDObjectives`); `EvaluateActiveObjectives` after every recorded fact.
- **CalledBy:** authored story chains (BP → `ActivateObjective` / `RecordProgress`), the SaveSubsystem (SaveTo/LoadFrom seams), the GameMode (HUD objective-line push), HUD/journal/audio via the `OnObjective*` + `OnStoryTagRecorded` buses.
- **Replicated:** server-authoritative evaluation (objective completion is run state — doc 06 authority map); clients receive pushed objective lines at P18+.
- **Saved:** raw facts ONLY — `story.tag.*` flags (the ledger), `objective.<id>.done/.failed/.active` flags, `objective.<id>.progress` counters. Activation is REPLAYED at load, never trusted wholesale: the ledger is the source of truth, completed rows re-complete from facts, active rows re-arm with progress (idempotent under load-time event storms — the power graph restores first and its events land in a still-empty ledger, then the replay matches it).
- **Server/Client:** evaluation server-side; HUD text is pushed from the same events clients already receive.
